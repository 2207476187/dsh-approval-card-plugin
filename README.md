# dsh-approval-card

审批卡最上面一行，写清「这次到底要动哪个文件、做什么」。

## 它解决什么

原来的审批卡经常只显示一句 `目标含工作区外路径 1 处：C:\Windows\Temp` —— 知道有越界，
看不到真正被写的是哪个文件。原因有两层：

1. 路径抽取在空白处切断，`D:\DeepSeek Harness工作目录\DeepSeek` 只剩 `D:\DeepSeek`；
2. 卡片正文由审批门自己拼（`操作：/路径：` 两行，路径最多 5 条、每条还被截断），
   而提权类请求的正文只是一句模型写的 `justification`，压根没有目标。

本插件在审批瀑布最前面改写 `displayReason.zh`，产出：

```
对 D:\DeepSeek Harness工作目录\DeepSeek\device-audit\report.json 进行写入文件 [ 写入 ]
权限：仅工作区可写（工作区外仍被拒绝）
<下游原有的拦截理由，原样保留>
```

- 目标优先取工具的**结构化参数**（`file_path` / `path` / …）原文，不截短、不猜；
  没有结构化参数时从命中语句里取路径（引号内整段、未加引号则向后接续到空白/选项/标点）。
- 命令里的 `$env:NAME`、`${env:NAME}`、`%NAME%` 会按宿主环境展开后再取路径 ——
  否则卡片上出现的是 `$env:DSH_HOME\…` 这种谁也不知道指向哪儿的字面量。
- `http://` `https://` 这类 URL 整体当一个目标（不会被 `p://` 这样的盘符规则切断）；
  语句里既有 URL 又有本地文件时，两个都会出现在理由里。
- 语句里连一个绝对路径都没有时，显示**命中的那条命令**（`对 命令行 node ..\audit.js --fix 进行运行程序 [ 执行 ]`），
  而不是只给一个「当前工作目录」——工作目录只是线索，能不能放行要看那条命令干什么。
  命令只有相对路径时，把工具参数里的 `workdir` / `cwd` 一并写出：`命令行 node test/x.mjs（在 D:\...\pkg）`。
- 宿主提权模板（`允许本次操作使用 <mode> 权限：<理由>`）只保留其中的**理由**，写成 `理由：…`；
  模式名已经由 `权限：` 行说清，同一句模式在卡片上出现两遍属于噪音。
- 下游理由按字段瘦身：`操作：`/`路径：` 行丢掉（那两行是审批门自己按空白截断的版本，与首行重复
  且更含糊），保留 `目标：`/`拦截：`/`原因：`/`网络外发：`；理由里被门扫出来的伪路径
  （`p://`、`/**`、正则片段、被截断的前缀）一并滤掉。
- 拿不到任何真实信息时**不改**，绝不编造目标。
- 只写 `displayReason`。`reason` 一个字不动 —— 上游的判定、审计与放行规则都在解析它。
- 只展示，不决定：永远 `return next()`，放不放行完全交给审批门与宿主应答者。

## 装法（本机）

它是 profile 的正式 bundle（这样才会出现在「已安装插件」列表里，并被启用/停用开关管理）：

1. `C:\Users\<user>\.dsh\profiles\desktop\package.json`
   - `dependencies` 加 `"dsh-approval-card": "file:plugins/dsh-approval-card"`
   - `dsh.profile.bundles` 里加 `"dsh-approval-card"`
2. `C:\Users\<user>\.dsh\profiles\desktop\node_modules\dsh-approval-card`
   → 指向 `plugins\dsh-approval-card` 的 junction（包名要能从 profile 解析出来）
3. 本包的 `cordis.patch.yml` 用**裸包名**插入自己：`name: 'dsh-approval-card'`
   （相对路径会相对 profile 目录解析，指不到 `src/`）

**不要再在 profile 的 `cordis.patch.yml` 里插一遍** —— 早期就是这么做的，改登记成 bundle 后
两处都留着会让同一个插件挂两次（同一张卡被改写两遍）。那三行已经删掉，只留注释说明。

改完要重启 DSH 才生效 —— 运行中的模块不会因为文件变化重新加载。

`client.js` 是浏览器半边，只做一件事：给审批卡标题补 `white-space: pre-line`。
不带它，上面那两行会被 CSS 折叠成一行（`_headline` 没有 `white-space` 声明）。
组合包启动时会校验每个 `dsh.client` 包能否解析出 `exports["./client"]`，缺文件会直接
抛 `ClientPackageCompositionError`；本机 DSH 能正常启动 = 这份 bundle 已被组合进前端。
它按 `/plugins/<包名>/<文件名>?rev=<rev>` 提供，`rev` 不匹配时返回 404（属正常，不是缺失证据）。

## 为什么 `prepend: true`

审批瀑布上任何监听器返回结果就结束整条链，而真正弹卡的应答者由更早挂载的组合包注册。
普通追加的监听器排在它后面，永远看不到待弹卡的请求。

## 自检

```powershell
node --test test/text.test.mjs
```

插件目录下的 `.activity.log` 是它是否在工作的外部证据：
出现 `apply` 行 = 运行中的 DSH 已加载它；出现 `rewrite:` 行 = 真的改写过文案。
日志超过 512 KB 会自动只留最后 200 行 —— 它只用于排障，不该无限长。

插件列表里的显示名「审批卡片」来自 `locale/zh.json` 的 `meta.title`（`locale/en.json`
是宿主读取整目录的锚点，缺它中文不会被读到）。改包名没有意义：`dsh-approval-card`
是模块说明符，被 `node_modules` 链接、`dsh.profile.bundles`、bundle patch 三处引用。

## 与 dsh-approval-zh 的关系

`dsh-approval-zh` 是同一需求的早期版本（逻辑已并入本包）。两者共存不会叠字：
本包用 `hasSummary` 判断「已经带总结」，见到就只做幂等处理。
建议只启用其中一个，避免同一张卡被两个插件轮流改写。

## 第三轮：URL 优先级 / 反斜杠还原 / 目标计数

- `preferLocal()`：命令里同时有 URL 和本地文件时，目标取本地文件
  （`Invoke-RestMethod … -OutFile C:\x\pkg.json` 真正被改的是后者）；只有 URL 时才回退到 URL。
- `unescapeBackslashes()`：审批门部分版本把路径再转义一层（`C:\\Users\\…`），
  展示前还原成单反斜杠 —— 否则卡片上的路径既难读也不能直接复制。
- 目标列表的条数改按**实际列出的项**计数：门报「3 处」但滤掉伪路径后只剩 1 条时，
  写「1 处」，避免「3 处」后面只跟一个路径。

## 第四轮：同一调用的重复审批要自报序号

一次工具调用可能被问两次：审批门先问「放不放行」，放行后工具再问「给不给更大权限」
（`dsh-sandbox` 的 `approveEscalation`）。两条请求各有独立的 id、各有一张卡，文案也完全不同，
用户看到的是「两件不相干的事」。

- `nextAskOrdinal(callId)`（`src/index.mjs`）：每个 `callId` 在内存里计数，**只数真的流到本插件的请求**
  ——被上游直接答掉的请求不计数，否则会给唯一那张可见的卡凭空标个「第 2 个」。
- `markRepeatOrdinal(zh, ordinal)`（`src/text.mjs`）：第 2 个及以后，在首行末尾追加
  `（同一次操作的第 N 个审批请求）`；幂等，重复调用不会叠两遍。
- 不改判断、不改 `reason`：编号只是让人知道「这张卡是接着上一张的」，点不点仍由应答者决定。

真机回放：354 条 `approval/asked` → 354 条改写、86 条带序号、`reason` 0 条被改。

## 第五轮：`cd` 的目标不是操作目标

`cd 'X' && node y.js --in C:\z\a.json` 里，`X` 只是换了执行目录，真正被动的可能是 `a.json`。
它偏偏排在语句最前面，不剔掉就会被当成「这次要动的东西」（线上出现过：目标显示成工作区，
实际改的是会话目录）。`pathsInStatement()` 现在先收一遍 `cd` / `chdir` / `Set-Location` /
`Push-Location` / `pushd` 的目标（含引号包裹、带空格的形式），再从候选里剔除。

`markRepeatOrdinal()` 另外修了两处细节：标记前削掉首行残留的空格；计数表淘汰时跳过刚写入的
那个 `callId`（否则同一个调用会被重新从 1 开始数）。

## 第六轮：一个路径都拿不到时别装样子

入口层探针（`probes/probe-handler.mjs`，用假 ctx 抓 `approval/request` 处理器）暴露了两处：

- 拿不到任何路径时总结行只剩 `进行命令执行 [ 执行 ]` —— 少了「对什么」这半边，与
  「有目标但很短」在版面上几乎一样，读者会以为已经显示了位置。改成 `对 未知位置 进行…`。
- 宿主只给 `escalate sandbox to <mode>: <理由>` 而不给 `displayReason` 时，
  `shouldAppendReason()` 把整条判为「不必附加」（假设理由已进总结），可总结里从来没有它，
  模型写的理由就这么消失了。现在只要解析出 `justification` 就补一行 `理由：…`。
- 同一 `callId` 的第 N 个请求如果本次**不需要改写**，之前不会标序号（标记只跟着改写走）。
  现在以「卡片上现有的文案」为基准标号，第 2 张卡一样能自报序号。

## 第七轮：门报了两处、卡片只显示一处

用户对照审批门自己的记录发现：`targets` 里明明有两处路径，卡片上只剩一处。用
`probes/probe-lastcard.mjs` 把最近 25 条真实审批的「门原文」与「卡片文本」并排比对，
找到两个吃路径的地方：

- **分号没当分隔符**。门有时把围栏结论接在同一行：
  `目标含工作区外路径 1 处：C:\…\Temp\dsh-x\plugin；破坏性动作：Remove-Item $keep -Recurse`。
  按 `,，、` 切分时「路径 + 句子」是同一个 token，里面有 `$`，被代码嗅探整条丢掉 ——
  那条工作区外的临时目录和拦截理由**一起**消失。现在先按 `；;` 拆成「路径段 + 尾随字段」，
  尾随字段按字段白名单（新增 `破坏性动作`）单独成行。
- **截断前缀被当噪声吞了**。门把目录写成 `…\dsh-approval-gate`，而首行写的是
  `…\dsh-approval-gate\src\paths.mjs`：它是同一个位置的不精确写法，之前直接滤掉，
  只剩一句没头没尾的 `目标含工作区外路径 1 处`。现在算作「同上」，明写成
  `（就是上面那个）`；与首行重复但确有第二处的，计数保留并注明 `（另有 N 处同上）`。

判定顺序也有讲究：先判「工作目录被截断的残片」（`D:\DeepSeek` 之于
`D:\DeepSeek Harness工作目录\DeepSeek`）—— 它同时也是首行文件的上级目录，但它不是
「另一处」，说「同上」会指错地方；剩下的才判「与首行同一位置」。


## 第八轮：门抢先把 reason 换掉，权限行整行消失

一次写三个工作区外目录的实测暴露：第二张卡（沙箱提权）只剩

```
对 C:\Windows\Temp\dsh-card-a.txt 进行写入文件 [ 写入 ]（同一次操作的第 2 个审批请求）
理由：按你的要求造一张「多个目录」的审批卡片，……
```

少了 `权限：完全访问（整机可读写、含系统位置、不可自动回滚）` —— 没人知道自己被要了什么权限。

原因：提权请求也会先过审批门，门判定「工作区外」后把 `reason` 换成了自己的中文块
（`操作：… / 路径：…`），模式标识 `escalate sandbox to <mode>` 就没了。插件原本只从
`reason` 解析模式，解析不出 → 不生成 `权限：` 行；同时因为宿主给了 `displayReason`，
`else` 分支被跳过 → 门的中文块也一起丢了。

修法两处：

1. 新增 `modeFromText()`：`reason` 里认不出模式时，退到 `displayReason` 的 zh/en 里认
   （模式标识或已本地化的中文名都认），把 `权限：` 行救回来；
2. `reason` 不是提权模板、而是门的中文块时，即使有 `displayReason` 也要把门的判断依据
   （目标/拦截/原因）附在下面，不再被 `if (hasZh) … else` 的互斥结构吃掉。

单测 37 条（新增「门先换掉 reason + 宿主模板」与「从中文模板认回模式」两组）。

## 第九轮：所有路径都写进「对 … 进行」之间

此前首行只写第一个目标，其余靠下游那行 `目标含工作区外路径 N 处：…` 补 —— 而那行是
审批门按空白截断过的，还常常退化成一句没有路径的统计。一次动三处目录时，卡片上
看起来只动了一处。

现在 `targetListFor()` 按「结构化字段 → 命令里每条语句 → 命令任意位置 → 申请理由」
逐层收齐，去重后全部写进首行：

```
对 C:\Windows\Temp\dsh-card-a.txt、C:\Users\Public\dsh-card-b.txt、C:\tmp\dsh-card-c.txt 进行写入文件 [ 写入 ]
```

配套三条规则：

1. 命令按 `;` / 换行切成语句逐段取目标（原来只取命中动词那一条语句，所以只写得出第一处）；
2. 子路径已说明同一件事时，上级目录不再单列（`New-Item C:\tmp` + `Set-Content C:\tmp\x.txt`
   只留后者）；
3. 首行列出的条数已不少于门报的处数时，下游那句 `目标含工作区外路径 N 处` 直接省掉 ——
   它不再包含任何新信息。列不全时照旧列出剩余项并标注「另有 N 处同上」。

单测 39 条（新增「三处目录全进首行」「结构化字段给了两个文件」）。

## 第十轮：门记的命令残句、重复的「原因」

重启后拿真机三目录的卡看，首行已经对了，但底下多两行噪声：

```
对 C:\Windows\Temp\dsh-card-a.txt、…、C:\tmp\dsh-card-c.txt 进行写入文件 [ 写入 ]（同一次操作的第 2 个审批请求）
权限：完全访问（整机可读写、含系统位置、不可自动回滚）
理由：按你的要求再造一张三目录的审批卡，验证首行是否列出全部路径。
目标：工作区外
影响：整机（工作区外任意路径可读写，含系统位置；改动不可自动回滚）
命令：$paths = @(                     ← 多行脚本的第一行，半句话
原因：按你的要求再造一张三目录的审批卡，…   ← 与「理由：」一字不差
```

两条规则：

1. `isTruncatedCommand()`：门把命令按换行截断记录，值以 `@(`、`(`、`{`、`[`、`=`、`+`
   结尾，或短到不足 12 字符又没有分隔符，就判定为残句，整行不显示；
2. `dropRepeatedFields()`：下游字段的值（去掉标签、小写）与已经输出的某一行相同时丢弃 ——
   门会把模型那句理由同时记进 `原因：`，与 `理由：` 重复。

顺带把伪路径也挡了：`\\?\$p`（设备前缀 + 变量）、`C:\tmp exists={0}`（格式串）来自脚本
里的字符串字面量，`JUNK_PATH_RE` 见到 `$ % { }` 或 `\\?\` 开头就不收。

单测 42 条。

## 第十一轮：同一件事只说一遍

用户看完真机第二张卡的要求：`命令：` 那行不要；`原因：` 和 `理由：` 重复，留 `理由：`；
`权限：` 和 `影响：` 重复，留 `影响：`。

`pruneRedundantFields(parts)` 就干这三件事，在拼成文本前统一裁剪：

| 行 | 规则 |
|---|---|
| `命令：…` | 一律不要（首行已经写明这次要动的目标，这行内容本身就是半句） |
| `原因：…` | 与某条 `理由：` **内容相同**时丢掉 —— 文案相同才叫重复 |
| `权限：…` | `影响：` 里出现「整机 / 任意路径 / 系统位置」时丢掉 —— 那时影响行已经把「会动到哪里」说全了 |

两条都是内容判定，不是标签判定：
- 门记的 `原因` 和宿主 `displayReason` 里的理由偶尔**不是同一句**，那时两行都留；
- `影响：工作区内的文件（可回滚）` 这种不足以替代 `权限：`，`权限：` 必须留 ——
  它说明这次放宽到的沙箱边界，是提权卡最该看的一行。

一个坑：首行和 `权限：` 是**同一个片段里的两行**（`buildSummaryLine` 一次返回 `对 … 进行…\n权限：…`），
按片段做 `startsWith('权限：')` 永远匹配不到。`pruneRedundantFields` 先 `flatMap` 摊平成行再判断。

裁剪后第二张卡：

```
对 C:\Windows\Temp\dsh-card-a.txt、C:\Users\Public\dsh-card-b.txt、C:\tmp\dsh-card-c.txt 进行写入文件 [ 写入 ]（同一次操作的第 2 个审批请求）
理由：按你的要求再造一张三目录的审批卡，验证首行是否列出全部路径。
目标：工作区外
影响：整机（工作区外任意路径可读写，含系统位置；改动不可自动回滚）
```

单测 47 条（含「原因与理由不同句时两行都留」「只放宽到工作区可写时权限行不能删」）。

复核时踩到自己的 bug：第一版把「权限：」的丢弃条件写成「有影响行就丢」，于是
`escalate` 但门没给影响行的那种卡（「权限：」是唯一说明边界的一行）整行消失 ——
单测 32、36 直接抓到。规则改成纯内容判定后恢复。
## 第十二轮：模式与理由还有第三个来源

真机复核发现另一条腿也会断：提权请求先过审批门，门把 `req.reason` 换成自己的中文块
（`escalate sandbox to <mode>: …` 整条消失），而处理器这时**不一定拿得到** `displayReason`。
结果那张卡只剩首行 —— `权限：` 和 `理由：` 都没了。

模式其实一直摆在工具参数里：提权请求必然来自一次带 `sandbox_permissions` 的调用。
于是 `applySummaryText` 现在按三条路认模式，前一条走空就走下一条：

1. `reason` 里的 `escalate sandbox to <mode>`；
2. `displayReason` 里的模式名/别名（`modeFromText`）；
3. 工具参数的 `sandbox_permissions`（`requestedModeOf`）。

理由同理：`reason` 被换掉时退回 `args.justification`（那是模型自己写的那句）。

```
门换了 reason、又没有 displayReason：
对 C:\Windows\Temp\dsh-card-a.txt、C:\Users\Public\dsh-card-b.txt、C:\tmp\dsh-card-c.txt 进行写入文件 [ 写入 ]
权限：完全访问（整机可读写、含系统位置、不可自动回滚）
理由：再造一张三目录的审批卡，验证裁剪后的文案。
```

## 第十三轮：第一张卡也要写全

同一次操作会弹两张卡（门问「准不准」，沙箱问「给不给权限」）。实测第一张卡只有首行，
缺 `权限：`、`理由：`、`目标：`、`影响：` —— 两个原因叠在一起：

1. 旧构建还没有 `requestedModeOf`，模式只能从 `escalate sandbox to …` 或 `displayReason` 认，
   而第一张卡两者都没有；
2. 上一轮为了不让门的字段块重复，我写成了「有理由就不附加门的块」的互斥条件 ——
   于是理由一旦能拿到，`目标：`/`影响：` 反而被饿死。

改成：门的字段块**不再看有没有理由**，只要它还有没写过的字段就附加（重复行由
`dropRepeatedFields` 去掉）；`shouldAppendReason` 的长度上限只对单行生效 —— 多行块是
字段清单，行数多不等于正文。

实测会话事件顺序（`tool/call` 索引 42 < 首次 `approval/asked` 43）证明第一次审批时
工具参数已经可读，所以第一张卡同样能拿到 `sandbox_permissions` 与 `justification`。
## 第十四轮：宿主把命令正文塞进「理由」槽

真机 13:47:56 / 13:48:55 两张写文件的卡，「理由：」后面显示的是命令正文的一截
（`'obj'} sp=${String(args?.sandbox_permissions)}` / `(typeof req.displayReason?.zh === 'string'…`）。
查下来：宿主构造提权模板 `允许本次操作使用 <mode> 权限：<理由>` 时，那个槽里放的不是
模型写的那句 justification，而是命令字符串本身；插件原先「模板尾部即理由」照搬，于是
卡片上摊开半截 here-string。

改法：

- 理由取值顺序变成「模型写的那句 justification → 模板尾部」，两者都要先过 `looksLikeCode()`；
- `looksLikeCode()` 判据：多行、长度 > 200、以 `(`/`[`/`{`/`` ` ``/`$` 开头、含 `@'`/`'@`/
  `${`/`$x.`/`Set-Content`/`Write-Host`/`Select-String`/`function `/`=>`/`| `；
- 两个来源都不可读时写 `理由：（宿主没提供可读理由）`，不再把代码当理由；
- 没有模板可拆（宿主给的这段本身就是成品）时整段照搬，不走 `looksLikeCode`
  （那张卡本来就有多行，拿代码判据卡它会整块丢掉 —— 这一步踩过，单测当场抓到）；
- `src/index.mjs` 同时补上按 callId 的完整文案缓存：第二张卡（沙箱提权）拿不到工具参数、
  门的 reason 又被换成中文块时，这一趟算不出新行，就复用同一 callId 上一趟写过的完整文案，
  不让它退化成「只剩首行 + 序号」。
